# Database implementation decisions

## In-center booking

Twenty migrations, `202611060001` to `202611060020`, add the feature, and `supabase db reset` applies them all from nothing. Clients have no direct writes on any booking table: every change is a `security definer` function that re-checks the caller, and a failed role check is an HTTP 403. Refusals raise a stable `booking_*` message, which each app turns into its own words.

Three things hold the rules together. One transaction lock, `pg_advisory_xact_lock(724020)`, covers every booking change, so a capacity count cannot race, and it also covers closures and settings. Two exclusion constraints stop overlaps for one patient and for one therapist, even from a direct insert. A trigger writes `booking_events` for every change, and everything downstream hangs from that table: the audit feed, notifications and the waitlist, so a new way of changing a booking cannot skip them.

`notification_deliveries` is the queue for email and push. A booking notification adds one row for each; exercise and care-team notifications (`202611130002`) add push only, and a push whose switch the reader turned off is added already `skipped` with the reason `Turned off`. `claim_notification_deliveries` takes rows with `for update skip locked`, so two runs cannot send one twice, and `finish_notification_delivery` retries with growing waits and stops as failed after 5 attempts. A push with nobody to reach ends as `skipped`, which is not a failure. `booking_series` groups the sessions of a weekly course, and `device_tokens` holds each phone's FCM token, owned by whoever signed in last.

The tables, functions and rules for booking are in [BOOKING.md](BOOKING.md). `center_problem` holds the rules that bind everyone, and `slot_problem` adds the ones that bind only patients: notice, horizon and the slot grid. Schedulers skip those, so they can book at short notice.

## Care chat

Migration `202611150001_care_chat.sql` adds a direct conversation between a therapist and a patient (issue #105).

| Table | What it holds | Rule |
|---|---|---|
| `conversations` | One row per therapist and patient pair, with the time of its last message | Created by a trigger when a link becomes active, and for every link already active. No direct access; read through functions |
| `chat_messages` | A message: its sender (null for a system note), kind (`text`, `attachment`, `progress`, `exercise`, `system`), up to 2,000 characters, and a `data` object for what a kind needs | The ID is made by the sender's device. Rows are written only by functions. `select` is granted with a row rule, for live delivery |
| `chat_reads` | How far each person has read each conversation | Written by functions; `select` with the same row rule |

**Who can do what.** `chat_can_send` is true for either person while the link is active, both accounts are active and the therapist still holds the therapist role. `chat_can_read` is true whenever sending is, and always for the patient. So when a link ends nobody can send, the patient keeps reading what was said to them, and the therapist loses the conversation exactly as they lose the patient's records, until the link is restored. Administrators and Schedulers have no rule that lets them in.

**Functions.** `my_conversations()` lists what the caller may read with the other person's name and photo, the last message and the unread count. `conversation_messages(conversation, before_at, before_id)` returns 50 messages newest first, by keyset, with how far the other person has read. `send_message(id, conversation, body)` returns the stored message; the same ID again returns the same message, so a retry cannot send twice, even after the link has ended. It refuses empty or over-long text (`chat_invalid`), a closed conversation (`chat_closed`) and more than 30 messages a minute from one person (`chat_rate_limited`). `mark_conversation_read`, `delete_message` (the sender only, within 15 minutes, leaving a mark and no words; `chat_too_late` after that) and `my_unread_messages` complete the set. There is no editing.

**Live delivery.** `chat_messages` and `chat_reads` are in the `supabase_realtime` publication. Supabase Realtime sends each change over a websocket only to connections whose user passes the row rule, so live delivery and reading can never disagree. A client must treat the connection as live only after Realtime reports that it is listening to the database, and must fetch again after any drop.

**The patient's agreement (#111).** Migration `202611150002_chat_consent.sql` adds the messages agreement, `care-chat-v1`, recorded in `consents` with `consent_type='care-chat'`. `chat_consented(patient)` reads the patient's latest answer to the current version. `chat_link_open` holds what `chat_can_send` used to; `chat_can_send` now also needs the patient's agreement, and `chat_can_read` uses `chat_link_open` for the therapist, so turning messages off stops sending both ways and leaves reading as it was. `my_conversations` and `conversation_messages` add `consented`. `send_message` refuses with `chat_consent_required` when only the agreement is missing. `my_chat_consent()` and `set_chat_consent(granted)` are for patients only; the same answer twice records nothing. `export_patient_chat(patient)` and `erase_patient_chat(patient)` are granted to `service_role` only, for the trusted operator answering privacy requests ([DATA-LIFECYCLE.md](../operations/DATA-LIFECYCLE.md#care-chat)); the second refuses without an open deletion request and writes an `erase` audit event.

**Photos and video (#106).** Migration `202611150003_chat_media.sql`. Files live in the private Storage bucket `chat-media` (6 MB per file, JPEG, WebP, MP4 and WebM only), at `<conversation>/<attachment>/media.<ext>` and `.../preview.jpg`. `chat_attachments` has one row per photo or video from the moment its upload is allowed; its ID is also its message's ID. Sending takes two calls around the upload: `start_attachment(id, conversation, kind, mime, width, height, duration_ms)` checks the agreement and the limits (photos at most 1600 px on the long side; video at most 480 on the short side and 854 on the long, and 30.5 seconds; 20 videos per conversation in 30 days; 5 unsent uploads per person an hour) and returns where both files go; `send_attachment(id, caption)` checks the stored files' sizes (1 MB photo, 6 MB video, 200 KB preview) and types against what was agreed, then creates the `attachment` message, whose `data` carries the file's kind, size, paths and `expires_at`, 15 days on. A file that breaks a limit is refused and queued for removal in the same call, so nothing is left behind. Two Storage policies decide access row by row: the uploader may write only the two paths they were given, within an hour and before sending, and nothing can be overwritten; reading is for the uploader while sending, and afterwards for the two people in the conversation until `expires_at`. A signed link is the only way to fetch a file. Taking a message back ends its file at once. `chat_media_trash` keeps the paths of files whose rows are gone, through a trigger. `chat_media_due`, `chat_media_removed` and `chat_media_usage` are for the cleanup (`scripts/cleanup_chat_media.py`) with the service key only; due files are expired ones, uploads abandoned for an hour, trashed paths, and any file over an hour old that no row names. Media needs `care-chat-v2`: `chat_media_consented` reads it, and `chat_consented` now accepts any version for words. `my_conversations`, `conversation_messages` and `my_chat_consent` add `media`.

**New-message notifications (#110).** Migration `202611150004_chat_notifications.sql` adds the `chat_message` kind, the `notify_chat_message` trigger on `chat_messages`, the `messages` push switch in `notification_settings`, and `chat_mutes` with `set_conversation_muted`. `mark_conversation_read` now also reads that conversation's notices. See [NOTIFICATIONS.md](../operations/NOTIFICATIONS.md).

**Cards, lines and scheduled messages (#109).** Migration `202611150005_chat_cards.sql`. `share_progress(id, conversation, progress, caption)` stores a `progress` message from a snapshot the app sends (the last four weeks, or one plan's latest, best and change), keeping only its known facts within sane bounds and stamping `as_of`. `share_exercise(id, conversation, assignment, caption)` lets the conversation's therapist send one of the patient's active plans; the server writes the card from the latest prescription version. A trigger on `notifications` turns a `practice_reminder` or `session_finished` into a `system` line through `chat_system_line`, keyed so a repeat adds nothing; `chat_open_between` checks a conversation can take it without a signed-in person. `my_conversations` leaves system lines out of unread counts and of the last line shown. `chat_scheduled` holds messages a therapist schedules with `schedule_message` (1 minute to 60 days ahead, 50 waiting at most), lists with `my_scheduled_messages` (the sender's own only) and cancels with `cancel_scheduled_message`; the `send-scheduled-messages` job runs `send_scheduled_messages` every minute, sending each once under its own ID, or dropping it with a reason if the conversation has closed.

**The conversation list under load (#112).** Migration `202611150006_chat_list_speed.sql` rewrites `my_conversations` to work out whether each link is open in one join, by the same rule as `chat_link_open`, instead of calling `chat_can_read` and `chat_can_send` for every row. Security-definer functions are not inlined, so those calls cost over 1 ms a conversation; for 150 conversations the list went from 569 ms to 28 ms on the local stack. `tests/contract/chat-load.test.ts` checks that the list and the two functions agree for every conversation.

## Exercise schedules

`202611170004_exercise_schedules.sql` (#125) puts a patient's exercises on a calendar. `exercise_schedules` holds a start and end date (inclusive, at most 366 days), rest weekdays (ISO, 1 is Monday; never all seven) and rest dates inside the range, for one therapist–patient link. `exercise_assignments.schedule_id` puts an exercise in a schedule; a composite key keeps it with the same patient. An exercise with no schedule is due every day, exactly as before, so older Android builds keep working. Patients and linked therapists read schedules through the same rule as assignments (`can_read_patient`). Nothing writes the table directly:

- `save_exercise_schedule` creates or edits one schedule, using an ID the client makes so a retry cannot create a second. Only an actively linked therapist can save, and only their own schedule. A new schedule starts today or later. Once a schedule has started, its start date and the rest dates behind it are fixed, so days already past are never rewritten. The end date is today or later, and at least one exercise day must remain. Refusals are named: `schedule_dates`, `schedule_rest_days`, `schedule_no_day` and `schedule_gone`; access is `42501`.
- `publish_scheduled_prescription` publishes through `publish_prescription` and puts the new exercise in the schedule, in one transaction. A later `publish_prescription` keeps it there, and an exercise cannot move to another schedule.
- `stop_exercise` takes one exercise off the plan. `end_exercise_schedule` ends a started schedule today and cancels one that has not started, stopping its exercises.
- `exercise_day(patient, day)` lists each active exercise with its schedule, whether it is due and whether it is done, and each current or coming schedule with its state (`upcoming`, `exercise`, `rest`), the exercise days left and the next one. It answers to the patient and their linked therapists only. Days are counted in the center's time zone (`center_date`). An exercise is done when a session for it started that day; a both-sides exercise needs a session on each side. Every session on the server is a finished one.

See the [design](../superpowers/specs/2026-11-17-exercise-schedule-design.md) and `web/tests/contract/exercise-schedule.test.ts`.

`202611170005_exercise_day_reminders.sql` (#127) sends the daily practice reminder only while an exercise due today is still to do.

`202611170006_missed_exercise_days.sql` (#128) adds `exercise_day_results`: one row per patient, therapist and finished exercise day, with how many scheduled exercises were due, how many were done and which were missed. It is read through `can_read_patient` and written only by `record_exercise_days`, which the `missed-exercise-days` job runs every 30 minutes. That job records the last three days once each, counting a day only from the day after an exercise was added, and from 08:00 to 20:00 sends the therapist one `exercise_missed` notification per patient and day with something left undone. The kind has its own push switch, `notification_settings.missed_days`, saved through a new optional `p_missed_days` that older apps leave as it was. The inactivity alert now follows every-day exercises only. `exercise_day` also returns the missed days of the last 30 for the patient record. See `web/tests/contract/missed-days.test.ts`.

## Google sign-in

Migration `202611230001_google_sign_in.sql` (#167). Supabase Auth links a Google identity to the account with the same verified email, and provisions a new email through the existing `on_user_created` and `provision_account` path: the patient role only. `on_email_confirmed` no longer adopts a pending sign-up's `patient_profile` metadata when the confirming account has a Google identity, so its details and privacy agreement are always the person's own. `my_sign_in()` (signed-in, active accounts only) returns `{password, google, profile_required}`: whether a password is set, whether Google is linked, and whether a Google patient with no staff role still has no patient profile. `delete_expired_signups()` is unchanged and never touches a confirmed account. See [GOOGLE-SIGN-IN.md](../operations/GOOGLE-SIGN-IN.md).

## Session videos shared with the therapist

`202611170007_session_videos.sql` (#129) adds the private bucket `session-videos` (20 MB, `video/mp4` and `image/jpeg`) and `session_videos`: one row per shared video, tied to one session, its patient and the therapist whose exercise it was. Sharing takes two steps, as chat media do. `start_session_video` agrees to the file and names its places (`patient/video/media.mp4` and `preview.jpg`), and only the patient whose session it is can call it, while that therapist is linked. It refuses video over 480p or five minutes, a second live share for the session, and more than five uploads an hour. `share_session_video` checks the stored files against the limits and shares for 15 days, or refuses and removes them, returning the refusal rather than raising it so the removal stands. `stop_sharing_session_video` ends it at once and queues the files. Reading the row or the file is limited to the patient and that therapist (`session_video_viewer`), not administrators. `session_video_due`, `session_video_removed` and `session_video_usage` serve `scripts/cleanup_chat_media.py`, which now cleans both buckets. Refusals are named `video_*`. See `web/tests/contract/session-videos.test.ts`.

## Both-sides sets and a time per side

`202611110001_bilateral_sets.sql` lets `publish_prescription` accept the side `bilateral` and an optional `side_seconds` parameter: a whole number of seconds from 15 to 1800, applied to each side. A both-sides prescription runs left, then right. The phone records each side as its own session against the same prescription version and consent. It uploads the side it measured (`LEFT` or `RIGHT`) with `bilateral: true` and, when the plan has a time, the matching `sideSeconds`. `ingest_session` rejects `BILATERAL` as a recorded side, a missing or misplaced `bilateral` flag, and a time that differs from the plan's. `session_measurements.side` stores the measured side, never `bilateral`, so each side keeps its own history and progress line. Uploads from older app versions omit both keys and still validate. The history side filter in both apps therefore matches `session_measurements.side` through an extra `measured:session_measurements!inner(side)` embed. No table or column was added. See [both-sides sets](../validation/BOTH-SIDES-SETS.md).

## Sprint 4 history reads

MOT-19 uses the existing RLS policies and schema. A history query fixes one patient and optionally filters the referenced prescription exercise version/side and inclusive UTC start-date range. The explicit `sessions_prescription_version_id_patient_id_fkey` embedding resolves the session's original immutable prescription, never the latest assignment version. All child measurements and tracking counts are retained. Keyset pages use `(started_at desc, id desc)` with a 50-row page and one lookahead; a newer concurrent upload cannot shift earlier pages. History is kept in memory only, cleared on account/filter change or request failure and refreshed through the authenticated API. No additional Room table, SQL migration or service credential is introduced.

The local API regression includes tied timestamps, a newer upload between pages, multiple child metrics, original targets after prescription edits, date boundaries, empty/interrupted fixtures, unauthorized reads and revoked access. See [history evidence](../validation/SPRINT-04-HISTORY.md). The S1–S3 records below remain historical implementation evidence.

## Sprint 3 contract

`202611010001_connected_workflow.sql` adds invitations, privacy requests and a development retention-policy row, plus prescription parameters, consent event IDs/times, session payload hashes/consent/duration and measurement quality/reason totals. Nullable paired extrema preserve unknown ROM rather than fabricating zeros.

Authenticated writes use `invite_patient`, `accept_patient_invitation`, `revoke_patient_link`, `publish_prescription`, `record_consent`, `ingest_session` and `request_patient_data`. Definer functions use an empty search path, explicit grants and internal role/ownership checks; direct authenticated inserts into sessions/measurements/prescriptions/consents are revoked to prevent bypassing validation. Patients never receive a service key. Invitations bind a hashed 48-character random code to the confirmed patient's email and expire after seven days; raw codes are returned once for manual sharing, not sent to email by the app.

Prescription requests have stable assignment/version UUIDs; an identical retry returns the existing version. Edits append a version under a per-assignment lock. Ingestion locks the session UUID and hashes canonical JSON; identical retries acknowledge the same result, while a conflicting payload is rejected. Ownership, active assignment/link, pinned exercise/side/targets/timing/form parameters, chronological consent and measurement validity are checked before parent/child writes commit. A withdrawn grant cannot authorize later sessions. Previously completed results remain readable to their patient; link revocation removes therapist access immediately.

Audit triggers append minimal actor/action/table/identifier events for role, link, prescription and privacy-request changes; invitations append a separate audit event. Tokens, invitation codes, video and pose traces are not audit payloads. Export/deletion requests remain `requested` until a trusted operator resolves them. The explicit development policy disables automatic deletion and sets review after 365 days. This is an engineering default, not a legal/clinical retention determination. The application does not claim a request has already erased data or expired backups. See [data lifecycle operations](../operations/DATA-LIFECYCLE.md).

Room v2 adds consent events, consent IDs, cache download time and outbox attempts/errors. Existing aggregate sessions remain intact; legacy unconsented pending payloads become `REVIEW_REQUIRED`. The session vault uses Android Keystore AES/GCM with an atomic, backup-excluded encrypted file scoped to the backend URL. Logout clears tokens/cache, retaining owner-scoped pending results. Worker credentials must match the outbox owner before a network write. See `docs/validation/SPRINT-03-IMPLEMENTATION.md` for current test evidence; the S1/S2 sections below are historical implementation records.

The authoritative entity relationships are in `docs/PLAN.md`; the executable schema is `supabase/migrations/202610310001_foundation.sql`. Fresh startup and reset have executed the migration and synthetic seed successfully. All 18 pgTAP access/integrity tests pass; `docs/validation/database-test-results.log` records the result. The live auth check also verifies signup provisioning and patient isolation through the API.

## Access matrix

Anonymous clients have no patient-table privileges. Active patients read their own profiles, role records, assignments, prescriptions, sessions and measurements; they cannot grant roles or alter prescriptions. Patients may append their own session results, measurements and consent events subject to ownership constraints. Assigned active therapists can read the linked patient's records and append prescriptions for an active assignment. Revoking a link removes that access. Administrators can review permitted records but role/link mutations remain trusted backend operations. Profile photos (`202611040002_profile_photos.sql`, moved to Storage by `202611170001_profile_photo_storage.sql`) add a server-written `profiles.photo_url`, readable under the existing row policy and with no client update grant. It holds a path in the public `avatars` bucket (`<account id>/<32 hex>.webp|jpg`, enforced by a check constraint), not an address. Issued upload paths are recorded in RLS-locked `profile_photo_uploads`; the only Storage policy on the bucket is an insert for the person a path was issued to, once, within the hour, so nobody can list, replace or delete files through a session. `profile_photos_due`, `profile_photos_removed` and `profile_photo_usage` are for the service-key cleanup only. Administrator directory search, overview counts, named links and the audit activity feed are read through `security definer` RPCs that re-check the active administrator role (`202611040001_admin_workspace.sql`). `admin_backend()` (`202611170002_admin_backend_status.sql`) returns only sizes and counts: database and Storage usage against the RLS-locked one-row `backend_plan`, `pg_cron` run history (reported as unknown where the scheduler cannot be read), the delivery queue and daily activity in the center's time zone. Child measurements inherit access through their session. Account activation and role membership cannot be edited by patient clients.

Sessions have client-generated UUIDs and a composite foreign key binding the prescription version to the same patient. The schema rejects negative counts and reversed/nonfinite ranges and end times preceding start times. Exercise/prescription versions and historical results/events reject in-place mutations. Atomic ingestion and conflict handling are Sprint 3 work; direct table inserts are not advertised as a completed synchronization protocol.

Indexes cover active therapist-patient lookups, active patient assignments, patient session timestamps and consent history; measurement primary keys cover parent-session lookup. Published exercise versions are immutable. A draft catalogue entry remains inactive/unpublished until therapist approval; publishing must append an approved version.

## Retention decision for this milestone

S2 adds app-private `motivance-sessions.db` using Room 2.8.5. `cached_prescriptions` stores only supported active assignments for the authenticated patient, their immutable prescription/exercise version, instructions, rules and 24-hour expiry. Cache refresh replaces an owner's cache transactionally; failed downloads preserve the last cache, and expired versions cannot start or resume a session. Offline revocations cannot be detected immediately. Release pilot policy must approve or shorten this freshness window.

`local_sessions` stores UUID, owner, pinned rules, aggregate ROM/counts/duration/quality totals, incomplete reason counts, UTC start/update/end and status. There are no stored camera images, videos or frame-by-frame poses. `sync_outbox` uses the same UUID as primary key and foreign key; completion and insertion commit together. Repeating a completed save returns the existing result. Conflicting ownership or changing a draft's prescription/start time is rejected. Demonstrations remain `LOCAL_ONLY`; prescribed sessions are `PENDING` for S3 ingestion. Upload acknowledgement, retry metadata, server reconciliation and progress aggregation are not implemented in S2.

All application reads filter by current owner. Sign-out deletes that owner's prescription cache and interrupts drafts; aggregate sessions/outbox remain under that owner so unsynchronized results are not silently lost. A different account sees none of them. Guest history is a separate development-only owner. The app disables backup and device transfer for its data. Room is not encrypted; approved local retention/deletion and encryption decisions remain pilot prerequisites. Authentication tokens are memory-only, so clinical offline continuation works only while an authenticated process remains alive; after restart, online sign-in is required before accessing that account's records.

Schema v1 is exported at `android/app/schemas/com.motivance.data.local.SessionDatabase/1.json`. S1 had no local database to migrate. No destructive fallback is configured; any future version must supply and test a migration. Android instrumented tests exercise file-backed reopen/recovery, atomic rollback on injected outbox failure, duplicate completion, account isolation, cache persistence/logout and immutable session configuration.

The local stack is for synthetic development data only. Integration checks remove the synthetic account records they create; the database reset command is confined to the disposable Motivance project. No production patient-data collection or retention period is enabled by this milestone. Records are not automatically cascade-deleted or silently expired. The owner must approve clinical retention, withdrawal/export handling and backup implications before the pilot. Implement a reviewed, audited purge procedure in that phase; do not bypass immutable-history controls ad hoc. This is a documented delivery boundary, not a claim of compliance with an unspecified clinical retention policy.

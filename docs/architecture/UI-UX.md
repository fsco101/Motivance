# Native UI and UX specification

The Stitch prototype in `stitch_galawgo_rehabilitation_system_prototype/` was removed from the repository on 2026-11-05 at the user's direction and remains in git history, but it is no longer the visual basis. From 2026-11-05 the user directed that its design be disregarded; the current visual system is the Motivance "motion arc" system described in [Motion arc design system](#motion-arc-design-system-2026-11-05). Do not package HTML/Tailwind or sample patient data into the application. Sections below that mention navy/teal tokens or the Stitch reference describe the earlier implementation history.

The native implementation now includes the reference's role-selection composition (branded header, introduction, stacked clinician/patient cards and portal actions), card-based patient/therapist home screens, bottom navigation, patient list, exercise list, progress and profile layouts, prescription form layout, camera positioning checklist, live preview controls and camera-check completion. Header/system bars respect safe drawing insets. The shared body color and pale-blue surfaces follow the clinical design tokens.

Dashboard names, patient lists, recent sessions (up to 20) and active assignment counts are loaded through authenticated Supabase requests and RLS. Loading, error and empty states are distinct. Logout discards overview data and late responses cannot repopulate it for a signed-out user. Role cards select a login portal, never grant staff privileges. Backend prescription writes, prescription-detail/guided sessions and ROM chart data integration remain scheduled work: the assignment form is visibly unavailable, ROM charts show an empty state, and ending the camera check never claims to save a rehabilitation session. Prototype patient names, numeric outcomes, accuracy/certification badges and institution claims are not copied into live records.

## Screen and state contract

Profile forms now use separate first-name/last-name inputs and grouped personal, contact and account sections. Error feedback appears beside edited or blurred invalid inputs, including malformed names, contact numbers, addresses and blocked usernames. Password confirmation mismatch and short registration passwords have inline guidance. Username checks run in both Kotlin and the database and cover curated multilingual terms plus common obfuscation. Native birthdate/history calendars expose localized date labels; birthdates cannot be in the future. Profile cards align avatar and identity in one header and separate muted labels from values for easier scanning. Historical full-name data is preserved until the user confirms split names. Evidence and filter limitations are in `validation/FORM-DESIGN-VALIDATION.md`.

Detailed patient signup collects full name, unique username, gender (including prefer-not-to-say), birthdate, address and contact number. Age derives from birthdate. Signup no longer offers bundled avatars. It notes that a profile photo can be added from Profile after email confirmation. Profile has a photo card with the system photo picker, upload progress, specific error messages (not configured, rate limited, unreadable, network) and a confirmed removal. Avatars throughout the app show the photo or the person's initials (see [CLOUDINARY.md](../operations/CLOUDINARY.md)). The final privacy agreement explains system-only uses and linked-therapist visibility; submission requires an explicit checkbox and valid fields. Consent is separate from movement recording and the server persists its policy version/time. Existing accounts without details can complete this form in Profile without inferred consent.

Profile displays username/avatar and demographic details, exposes an edit form, and displays email as read-only text. Change password requires the current password, a different password with at least eight characters and a matching confirmation; credentials remain transient and clear on submission. Loading/errors/success are explicit. Linked therapist patient cards show username/avatar/age, and patient detail shows name, birthdate, age, gender, address and contact. Server RLS limits reads to the owner, active linked therapists and authorized admins. No demographic data is copied to the exercise cache or token vault.

Login provides loading, neutral recovery acknowledgement, confirmation-required and failed-request states. Passwords and OTP codes are not saved with Compose saved state. S1 uses memory-only tokens and requires sign-in after app restart. A user with multiple trusted roles will choose a workspace only from roles returned by the server. A missing backend configuration produces an actionable error; the camera feasibility screen is independent of authentication because it records/uploads no data.

The implemented auth flow now shows one form at a time: Sign in -> Register -> Confirm email, or Sign in -> Request recovery -> Verify recovery/new password. A back-to-sign-in action is available from secondary forms. Registration/recovery acknowledgements move to their corresponding code-entry forms. Client validation rejects missing email/password/code before contacting the server. Busy state disables repeated actions, including while logout cleans up remotely. Failed refresh clears the visible session and uses a localized session-expired notice. Backend error payloads are not displayed verbatim. The authenticated shell displays only server-returned roles; complete workspaces remain scheduled for later sprints.

Camera setup explains secure phone placement and visible joints before requesting camera permission. Denied permission leaves a retry/back path; permanently denied users can enable the permission through Android settings. Camera absence or model failure has readable text and an exit. Backgrounding releases the camera and discards the rendered frame. S1 provides no fabricated angle, repetition count or target-success indicator.

The camera screen includes an app-settings shortcut when permission is denied and rechecks permission on resume. System Back returns from the camera to the auth shell. Camera errors and diagnostic labels use English/Filipino resources. A zero-size camera canvas does not construct an invalid coordinate transform, which protects transitions and large-text layouts from a geometry crash. Physical accessibility validation is still required.

The skeleton prototype displays the same rotated bitmap used for inference, centered with letterboxing; mirrored front-camera landmarks use the same geometry. Tracking lost is communicated in text as well as marker visibility. In S2, the agreed clinical quality gate must be stricter and joint-specific. Place future Start/Pause/Finish controls within comfortable reach and keep the joint view unobstructed, following the reference camera HUD.

Patient screens must specify empty assignment, expired assignment, offline cached, missing instructions/model, tracking lost, interrupted and pending/rejected upload states. Therapist screens need empty list, loading, access revoked, invalid targets and prescription-version change states. Sample values and disabled future features must never appear as real patient progress.

## Workspace consistency and action feedback

The overall workspace refinement uses the shared `ClinicalCard`, `ActionButton`, `LoadingNotice`, `FeedbackNotice` and `EmptyState` components. White surfaces, pale blue backgrounds, restrained navy/teal accents, system typography and consistent 20dp card padding extend the existing authentication design. Patient and therapist home cards give their primary workflow visual priority; camera checks are secondary. Scrollable content caps at 720dp and the landing page at 640dp. Shared action buttons have a 56dp minimum height and wrapping labels.

Detail screens expose a labeled Back action: prescription to patient detail, patient detail to directory, and local history to Profile (or the unauthenticated completion screen). Related bottom-navigation destinations remain selected on detail screens. Admin navigation goes directly to Administration instead of a patient-labelled duplicate. Changing destinations starts at the top of the new screen. Administration has Overview, Accounts, Links, Catalogue and Activity sections in a scrolling chip row that keeps the selected chip visible. The Overview shows server-wide counts and attention items that lead to the section resolving them. Accounts are searchable and filterable with expandable detail cards. Links use account pickers grouped by therapist. Catalogue editing is opt-in with character counters. Every change is confirmed in a dialog naming the affected record (see [ADMIN-WORKSPACE-REDESIGN.md](../validation/ADMIN-WORKSPACE-REDESIGN.md)); history filters and advanced prescription timing expand on request. Invalid date feedback remains visible when filters collapse.

Rehabilitation, authentication and administrator state identify the active operation. Progress text distinguishes refreshing, inviting, connecting, publishing, preparing uploads, saving consent and submitting privacy requests. Busy actions reject repeat submissions. Shared notices announce politely, and errors offer a retry where applicable. Empty assignments do not appear while loading or after a failed workspace refresh. Sync scheduling reports a request, while individual outbox records alone report acknowledged upload; privacy submission still reports awaiting review. See [WORKSPACE-UI-REFINEMENT.md](../validation/WORKSPACE-UI-REFINEMENT.md) for executed evidence and limitations.

## Accessibility and consent review

Use English/Filipino resources for patient-critical text; review clinical wording with the therapist. Do not convey progress solely by color or icons. Support large font and screen-reader labels. Avoid flashing tracking feedback. Camera permission and patient data consent must be separate actions. The S1 screen is a local camera prototype and explicitly states it does not collect rehabilitation records.

Pending evidence: therapist wireframe review, representative patient comprehension testing, screen-reader/device checks and large-font screenshots. This specification plus the theme is implementation input, not a claim that user review occurred.

## Sprint 2 implementation update

The camera flow now follows the Stitch assessment pattern with a live skeleton, readable quality banner, measured angle, prescribed/demo thresholds, rep target, ROM, incomplete count, active duration and text feedback. All critical new copy has English/Filipino resources. The preview uses a fixed-height letterboxed surface inside a scrolling screen so controls remain accessible on smaller displays. Current frame geometry and assessment timestamp come from the same inference result; filtered angle deliberately lags raw skeleton movement by approximately one valid frame.

Step 1 of the assignment editor lets a therapist add a custom exercise inline, so the rest of the assignment is kept, and selects it on saving. Custom exercises show the joint they measure and a remove action that asks first. Their therapist-written name replaces the translated exercise name on patient screens.

Development exercise/side chips are available before demo session creation, and only to accounts with no valid assignment: a valid assignment replaces demo rules whenever no session is active, and a new session keeps the assignment in use. Assigned prescription sides/targets cannot be changed through those chips. Supported downloaded patient prescriptions have a distinct selection and show their cached instructions. Rules freeze when a session starts. Start is gated by fresh stable visible joints and separate consent to store aggregate metrics. Pause, finish/save retry, explicit interrupted recovery, saved summary and owner-filtered history are implemented. A local save is distinguished from an acknowledged upload. Demo controls cannot start measurement in release builds. S1 statements above describe its historical boundary; current recording stores aggregate results after consent, while continuing to store no images/video/pose traces.

## Authentication design refinement

Loading, login, patient signup, email confirmation and password recovery share a pale mint/blue background, supplied Motivance logo, navy headings, teal portal label and white 24dp-radius form surface. Forms cap their width at 480dp, scroll on compact displays and account for the keyboard. Primary buttons remain at least 56dp high; the camera setup is a secondary action. Login copy distinguishes patient and therapist workspaces, and the therapist portal does not offer patient signup.

Startup displays an indeterminate branded loading screen only while checking the stored session, with no artificial delay or percentage. Failed/empty restoration returns to the unauthenticated flow. Form submission shows an action-specific loading label and disables repeat submissions/navigation. Notices use readable text and a polite accessibility live region. Email keyboards, Next/Done actions, show/hide password and separate new-password/code labels support the forms. Switching forms clears passwords, codes, visibility and stale notices; passwords and codes are never stored in saved instance state. Email and the current form survive configuration recreation. New copy has English and Filipino resources.

This refines the existing email/password flow without adding Gmail authentication, media sharing or a new sprint. Evidence is recorded in [AUTH-UI-REFINEMENT.md](../validation/AUTH-UI-REFINEMENT.md). Physical-device, TalkBack and therapist wording reviews remain deferred in the post-implementation checklist.

## Sprint 4 history and progress

Progress and therapist patient detail now share native history filters and Canvas charts. Therapists first choose one linked patient; patients are fixed to their own account. Filters select an exercise definition version, anatomical side and optional inclusive UTC calendar dates. Invalid or reversed dates show a correction message and hide earlier results. Loading, no matching uploads, failed access/network, refresh and older-page states are explicit. Pending offline records remain in Local history until uploaded.

Each chart identifies its immutable prescription version, original degree/repetition targets, metric, model and algorithm. Different prescriptions, exercise versions, sides and provenance never share a line. ROM and completed repetitions have separate labeled scales; the horizontal axis is chronological session order. Limited, invalid, interrupted or missing metrics leave gaps. Detailed cards retain all child metrics, extrema/ROM units, counts, tracking quality/frame totals and completed/partial/interrupted/empty/invalid status. Charts summarize the loaded pages only and make no clinical-improvement claim. New copy has English and Filipino resources; terminology and physical accessibility review remain deferred.

## Motion arc design system (2026-11-05)

The user asked for a mobile UI/UX and interaction overhaul that disregards the Stitch prototype. The direction is drawn from the supplied Motivance logo and from the product's own subject: a joint's range of motion.

**Tokens** (`designsystem/MotivanceTheme.kt`, object `Motion`). Ink `#0D2B36` (text, hero surfaces), Lagoon `#0E7C86` (primary actions), Sprout `#1B7F45` / bright `#6FE08F` (a reached or prescribed range), Mist `#F1F6F5` (page ground), Amber `#E8A33D` (caution and hold only). The camera session uses a separate dark `SessionTheme` (Night `#062229`, panel `#0E3640`). Amber never signals success, and progress is always also stated in text.

**Type.** Bricolage Grotesque (OFL, bundled in `res/font`, licence in `assets/licenses/`) for headings and the numbers patients watch: angles, repetitions and targets. Body copy stays on the system face so long Filipino words wrap predictably at large font scales. All-caps labels were removed from both locales; the Filipino tagline's corrupted `?` separators were fixed.

**Signature element.** `MotionArc`, an open 240° goniometer face, appears in a single orchestrated landing animation, the patient's Today card (prescribed band plus reach angle), empty states, local history and the session-complete summary. `RangeArc` remains the 0–180° protractor; in the therapist prescription editor both ends can be dragged, snapping to 5° and staying at least 15° apart, with haptic ticks. The typed angle fields remain the precise and accessible input.

**Screens.**
- Landing: arc hero, one Sign in action, camera trial, language segmented control.
- App bar sits on the page ground and shows the signed-in person's avatar; the development pill appears only before sign-in.
- Patient home: greeting, Today card that starts the next valid downloaded assignment directly (falls back to the orientation hero when none is cached), Monday–Sunday completed-session strip built from uploaded and on-device sessions.
- Therapist home: counts, the first three linked patients as a tappable grouped list, and See all.
- Patient list: grouped rows that open the patient record; revocation stays behind the overflow menu and confirmation dialog. Invitation codes have a Copy action that confirms in place.
- Exercise cards: the prescribed band on the protractor, range/repetition pills, Start, and download/version metadata behind Show details.
- Camera setup: drawn positioning illustration and a numbered checklist (the steps are a sequence).
- Live session: full dark stage including system-bar areas (`designsystem/Stage.kt`), tracking status chip on the image, larger angle/repetition readouts with a rolling count, then the measurement controls, then the counting rules. Recording shows a pulsing indicator.
- Session complete: arc filled by completed/target repetitions with ROM, not-counted and active-time blocks.

**Interaction.** Page transitions slide by navigation depth and fade between tabs (`AnimatedContent`). Pull-to-refresh is available on workspace pages; its indicator only shows for a refresh the person started, and the explicit Refresh button remains for accessibility. `Collapsible` animates disclosures (invitation, timing, filters, details). `TappableSurface` settles slightly under a press. Haptics (`designsystem/Interaction.kt`) tick on selection, tab changes and arc snapping, and confirm counted repetitions, measurement start, copy and a saved session. Compose animations follow the system animator scale, so disabling animations removes them.

No database, backend, authentication, assessment rule or consent behaviour changed, and no runtime dependency was added. Evidence: [MOTION-ARC-REDESIGN.md](../validation/MOTION-ARC-REDESIGN.md).
